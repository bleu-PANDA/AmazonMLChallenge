## 1. Executive Summary

We built a lightweight, end-to-end entity resolution pipeline that matches business records
from two noisy sources (S2, S3) against a deduplicated reference set (S1).  Our approach
combines multi-signal inverted-index blocking (84% recall ceiling), 23 engineered string-
similarity features, and a LightGBM binary classifier tuned directly for F_0.5, achieving
**0.91 validation macro F_0.5** with 95% precision.

---

## 2. Methodology

### 2.1 Problem Analysis

Key insights from exploratory data analysis:
- **Script variation**: ~30% of India matches use Devanagari/Tamil/Kannada script in S2/S3
  against Latin script in S1 (e.g. "एसएस फूड" vs "Ss Food").  Solved with `text-unidecode`
  ASCII transliteration.
- **Name noise**: Typos (Wilblims→Williams), legal suffix variation (Corp/Corporation/Inc),
  DBA/trade names (zblue.com vs Zander Blue Co), word-order swaps.
- **Address noise**: ~3.3% of S2/S3 addresses are missing entirely.  Component reordering
  (state before city), abbreviations (Rd→Road, St→Street), leading zeros on house numbers
  (0684→684), and landmark-based references (Near SBI ATM).
- **Singletons**: 5.6% of S1 entities have zero matches — correctly predicting empty = 1.0
  credit; any false match = 0.0.
- **Country distribution**: Training covers US (60%) and India (40%).  Test adds France
  (15%).  Our pipeline treats country as an open string label, never hardcoded.

### 2.2 Solution Strategy

**Approach Type:** Blocking + Feature Engineering + Gradient-Boosted Classifier  
**Core Innovation:** Counter-weighted candidate ranking in blocking (key overlap count × 15 + name similarity + address similarity) to maximize recall ceiling within a fixed candidate budget; lazy target preprocessing during inference to handle 10M+ target records efficiently.

---

## 3. Candidate Generation (Blocking)

We use an inverted index with multiple overlapping key types per record:

| Key Type | Example | Purpose |
|----------|---------|---------|
| `country:tok:<token>` | `US:tok:payne` | Match on any core business name token (≥3 chars, excluding legal suffixes) |
| `country:p4:<prefix>` | `US:p4:payn` | 4-char prefix for typo tolerance |
| `country:pair:<tok1>_<tok2>` | `US:pair:payne_enterprises` | Sorted pair of first 2 tokens for specificity |
| `country:num_addr:<num>_<word>` | `US:num_addr:3315_fremont` | House number × street word — strong geographic signal |
| `country:num_name:<num>_<tok>` | `US:num_name:3315_payne` | House number × business name — cross-field signal |

**Pruning**: Keys with > 500 postings are removed to prevent combinatorial explosion on
generic tokens like "services" or "national".

**Candidate ranking**: When a query retrieves > K candidates, they are scored by
`key_overlap_count × 15 + token_sort_ratio(name) + 0.2 × token_set_ratio(addr)` and the
top-K are retained.  This boosts recall ceiling by ~10% over simple name similarity ranking.

- **Blocking recall ceiling**: ~84% (on validation split)
- **Reduction ratio**: 99.99%+ (< 20 candidates per entity vs millions possible)
- **How true matches were not lost**: Multiple overlapping key types ensure that even when
  names are very different (transliteration, DBA names), address number × word keys or
  prefix keys still fire.

## 4. Matching Model

**Features used (23 total):**
- **Name features (9):** Levenshtein ratio, partial ratio, token-sort ratio, token-set ratio,
  Jaro-Winkler similarity, token Jaccard, core exact match flag, length difference, length ratio
- **Address features (8):** ratio, token-sort ratio, token-set ratio, partial ratio, token
  Jaccard, number Jaccard, common-number flag, length difference, missing-address flag
- **Metadata (3):** country exact match, is-S2 flag, is-S3 flag
- **Interactions (2):** name × address sort ratio, name × address number flag

All features are computed using `rapidfuzz` (MIT License, C++ backend) for speed.

**Model type:** LightGBM (MIT License) — 150 estimators, 31 leaves, learning rate 0.05  
**Total parameters:** ~10K (well under 8B limit)

**Threshold selection:** We scan thresholds 0.20–0.90 in 0.05 steps, computing the exact
macro-averaged F_0.5 (including singletons) on an entity-disjoint validation split, and
select the threshold maximizing F_0.5.

**Assumption on negative pairs:** Negatives are all non-matching candidates generated by the
blocking stage.  True positive matches from the ground truth that were not in the blocking
candidate set are injected as additional positives to avoid training-set bias.

---

## 5. Results & Error Analysis

- **F_0.5 Score (macro):** **0.91** (validation, 5000 S1 entities, entity-disjoint)
- **Precision (macro):** 0.95
- **Recall (macro):** 0.83
- **Blocking recall ceiling:** 84%

- **Common false positives (wrong merges):** Businesses with identical generic names
  (e.g. "National Services Ltd") at different addresses in the same country.
- **Common false negatives (missed matches):** Transliterated names where the ASCII
  rendering is too different from the English name (e.g. "eses phuudd" vs "ss food"),
  and DBA/trade names with no token overlap (e.g. "Dréxkor" vs "Maure Williams").

---

## 6. Conclusion

Our pipeline achieves strong precision (0.95) and reasonable recall (0.83) using only
rule-based text normalization, inverted-index blocking, and a lightweight LightGBM
classifier.  The key enablers are: (1) multi-signal blocking keys that generate overlapping
candidates even when names differ greatly, (2) Counter-weighted candidate ranking that
maximizes recall within a fixed candidate budget, and (3) direct threshold tuning on
macro F_0.5.  The pipeline handles the unseen France country without any code changes.
